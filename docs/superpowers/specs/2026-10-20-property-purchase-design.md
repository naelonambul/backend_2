# Property Purchase and PortOne Payment Design

## Goal

Let a buyer pay the full listed price from a property detail page. The backend must retrieve and verify the payment through the PortOne V2 API before completing an order. Persist purchase records in SQLite and prevent duplicate or concurrent purchases of one listing.

## Agreed scope and constraints

- The frontend is the Vue app in `frontend/`; the backend is the FastAPI app in `app/`; the default database is SQLite `app.db`.
- The configured `PROPERTY_SELLER_EMAIL` account is the only seller. Other authenticated accounts are buyers.
- A buyer must be signed in to pay. The seller cannot buy a property, including their own listing.
- The amount comes from `Property.price_krw` in the database, never from a client-supplied amount. Currency is `KRW`.
- Use PortOne V2 with a Toss Payments new-module channel. Do not modify existing PortOne console settings.
- Property title transfer, escrow, contract creation, and legal or tax processes are out of scope.

## PortOne configuration and secrets

At the time of inspection, the selected PortOne store had no test or live payment channel. Registering a Toss Payments new-module channel requires the PG MID, PG secret key, and client key in the PortOne console. This design and implementation do not create a channel or change console values.

After a channel is configured, the app reads the public `storeId` and `channelKey` issued for that channel, plus a server-only PortOne V2 API secret, from environment variables.

- Public frontend variables: `VITE_PORTONE_STORE_ID`, `VITE_PORTONE_CHANNEL_KEY`
- Backend-only variable: `PORTONE_API_SECRET`
- The PG MID, PG secret key, and client key belong in the PortOne channel configuration, not application source, frontend bundles, or the repository.
- `.env.example` contains empty values or explanatory placeholders only. The actual `.env` is not committed.
- If a required runtime value is missing, the purchase creation API returns a clear configuration error. Secrets must not appear in responses or logs.

## Data model

Keep the existing `property` table and add a `purchase` table. Derive a property's reservation or sale state from purchase records, so no payment-specific column is added to `property`.

`purchase` fields:

- `id`: server-generated UUID primary key
- `payment_id`: unique PortOne payment identifier generated by the server
- `property_idx`: foreign key to `property.idx`
- `buyer_user_idx`: foreign key to `user.idx`
- `amount_krw`: listed price copied from the database when the order is created
- `currency`: `KRW`
- `status`: `pending`, `paid`, `expired`, `failed`, `cancelled`, or `refund_pending`
- `expires_at`, `created_at`, `paid_at`: expiry and audit timestamps

A SQLite partial unique index allows at most one purchase per property in `pending`, `paid`, or `refund_pending` state. In a transaction, order creation first expires stale `pending` rows and then inserts a new order. A unique-index conflict maps to a response saying that the property is already reserved or sold. Keep `paid` records as purchase history. Keep a `refund_pending` order active until cancellation is confirmed so the property cannot be sold twice while money may still be captured.

An order reserves the property for 15 minutes. Once expired, another buyer may create an order. If a payment for an expired order is later found to be paid, do not complete that sale; request a full PortOne cancellation instead. If cancellation fails, keep the order in `refund_pending` and block another sale until it can be resolved.

## Payment and API flow

### Create an order

`POST /properties/{property_idx}/purchases`

- Allow only an authenticated buyer. Return 401 when signed out and 403 for the seller or a self-purchase.
- Return 404 when the property does not exist and 409 when it is already reserved or sold.
- Read the amount and property title from the database, generate a unique `payment_id` and a 15-minute expiry, and persist a `pending` order.
- Return only the order ID, payment ID, order name, amount, currency, and expiry needed to open the payment UI. Never return the PortOne API secret.

### Toss Payments checkout

- Show the full listed price and a purchase button on the property detail page to a signed-in buyer.
- The frontend calls the PortOne V2 SDK `requestPayment` with public `storeId` and `channelKey`, the server-issued `paymentId`, `KRW`, the server-issued amount, and the card payment method for Toss Payments new module.
- Treat the SDK result or redirect as a signal to start server confirmation only. Do not complete an order using a browser amount or success flag.
- Preserve the order identifier in session state for redirect return. On return, verify the signed-in user owns the order before calling the backend confirmation API. Do not store sensitive values in the URL or browser storage.

### Verify and complete on the server

`POST /purchases/{purchase_id}/confirm`

- Only the authenticated buyer who owns the order may call this endpoint.
- Check that the request `payment_id` matches the server-issued ID stored on the order.
- Use `PORTONE_API_SECRET` to retrieve the payment from the PortOne V2 payment API.
- Verify the payment ID, `PAID` status, exact total amount, and `KRW` currency against the stored order.
- If payment is not yet complete or cannot be retrieved, do not mark the property sold. Retries must be idempotent.
- If the order is still valid and is the property's only active order, mark it `paid` in a database transaction. If the order expired or a uniqueness conflict shows another order won, request a full PG cancellation.
- Do not complete a payment with an amount or currency mismatch; request a full cancellation. Record successful cancellation as `cancelled`; if cancellation fails, record `refund_pending`.
- For PortOne communication or cancellation errors, return a retryable error without logging the payment ID together with secret values.

### Property detail and availability

- Add `availability` to `GET /properties` and `GET /properties/{idx}`: `sold` when a successful purchase exists, otherwise `reserved` when an unexpired active reservation exists, otherwise `available`.
- Disable the purchase button and explain the status for `reserved` or `sold` properties. The atomic order-creation API is the authority; UI state is not a security boundary.

## Frontend behavior

- Show the full price and a `Buy property` button on the property detail page.
- Send signed-out users to login and return them to the original detail page afterward.
- On click, run order creation, Toss Payments checkout, and server confirmation in that order.
- Prevent repeated clicks while the request is in progress. Distinguish processing, cancellation, failure, server verification, and completion states.
- On verified success, show purchase completion and refresh property availability. Do not show completion based only on a browser payment response.

## Errors and security

- Recheck the authenticated user, property, and purchase ownership in each relevant API.
- Ignore any client-supplied price and compare exact integer KRW amounts.
- Do not expose the PortOne API secret, PG secret, or session tokens in the client bundle, responses, or logs.
- Use unique IDs and idempotent state transitions for order creation, confirmation, and cancellation.
- Missing payment configuration returns 503; a property reservation conflict returns 409; an unverified payment never completes an order.
- Asynchronous recovery in this scope relies on the buyer returning from checkout and retrying the confirmation API. PortOne webhook handling and an operator refund dashboard are out of scope.

## Verification

- Pytest: unauthenticated and seller denial, self-purchase denial, server-derived amount, order creation, reservation expiry, duplicate and concurrent order prevention, PortOne success/unpaid/amount mismatch/currency mismatch/API error, cancellation of late approval, `refund_pending` on cancellation failure, order ownership, and idempotency.
- Mock the PortOne API client so the full backend suite runs without an external PG or merchant credentials.
- Jest: purchase button and availability states, login redirect, order creation and SDK arguments, successful server confirmation, cancellation/failure/verification errors, and duplicate-click prevention.
- Use Chrome DevTools to inspect the purchase flow on the detail page, redirect return, and error states. A real PG approval can only be checked after configuring the Toss V2 channel key and PortOne V2 API secret.
- After integration, run the project's full `pytest` suite and frontend Jest suite.

## Alternatives considered

1. Mark the listing sold based only on the browser payment response: rejected because client responses can be forged.
2. Add only a `sold` flag to the property table: rejected because it does not preserve order history, payment IDs, or refund tracking.
3. Add a purchase table, verify payments on the server, and use a partial unique index for active orders: selected because it provides auditable purchase history and duplicate-sale prevention.
